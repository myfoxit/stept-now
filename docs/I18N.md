# Internationalisation

Stept ships **13 languages**: English plus German, French, Spanish, Brazilian
Portuguese, Italian, Dutch, Polish, Turkish, Japanese, Korean, Simplified
Chinese, and Arabic (right-to-left).

Before this, the repo had no i18n of any kind — no library, no catalogs, no
locale column, no `Accept-Language` handling. `docs/CHATWOOT-BACKLOG.md` §2.6
had flagged the gap and recommended building the framework early, precisely
because retrofitting extraction across the test suite gets more expensive with
every wave.

---

## One format, four runtimes

The backend, the dashboard, the widget and the extension all read the same
catalog shape, so a string can move between surfaces without being rewritten and
one guard can police all of them.

```jsonc
{
  "inbox.reply_placeholder": "Write a reply…",     // flat dotted keys
  "csat.star_one": "{{count}} star",                // {{name}} interpolation
  "csat.star_other": "{{count}} stars",             // CLDR plural siblings
  "csat.star_few": "{{count}} gwiazdki"             // …as many as the language needs
}
```

Flat keys beat nested ones for a file that is diffed and machine-checked: a
missing key is one missing line, not a collapsed subtree.

| Surface | Runtime | Catalogs |
| --- | --- | --- |
| Backend | `backend/app/core/i18n.py` | `backend/app/i18n/<locale>.json` |
| Dashboard | `frontend/src/i18n/` | `frontend/src/i18n/catalogs/<locale>.json` |
| Widget | `widget/src/i18n/` | `widget/public/i18n/<locale>.json` |

### Why not i18next

i18next earns its ~40 KB on namespaces, pluggable backends and a plugin system.
What these surfaces need is lookup, interpolation and plurals — and
`Intl.PluralRules` supplies correct CLDR categories for free, so the browser
runtimes agree with the backend's hand-written rules without shipping a rules
table. The one real loss is `<Trans>`; `tParts` covers that case (below).

Python has no `Intl`, so `plural_category` implements CLDR for the thirteen
shipped locales by hand. Adding a locale means adding its rule there *and* to the
test fixture — deliberate friction, because a locale whose plurals silently fall
back to English is worse than one we never shipped.

## The rule that matters: the visitor's language wins

Most chat widgets read `navigator.language` and stop. That gets the common case
right and the interesting case wrong: someone on a borrowed laptop, a shared
kiosk, or a browser still on its factory `en-US` types a question in Turkish and
gets answered in Turkish — inside an English interface.

So the widget's strongest signal is **what the visitor actually writes**:

1. `learned` — the language detected from their own messages, stored on the
   contact. The only signal that is evidence about *this person*.
2. `explicit` — `SteptSettings.locale`, the host page's setting.
3. `navigator.languages`.
4. the workspace default.

```html
<script>
  window.SteptSettings = {
    workspaceKey: 'wk_…',
    locale: 'de',        // optional: a starting language
    lockLocale: true,    // optional: keep it even against what they write
  }
</script>
```

`lockLocale` exists for the regulated single-language product and the screenshot
harness. It is off by default, because a visitor writing Turkish is better served
by a Turkish interface than by the one the site owner assumed.

Detection lives in `backend/app/services/language.py` and is **not** an LLM call.
The model already mirrors the customer's language without being told which one it
is; what a model cannot do is tell the widget which language to render its
buttons in *before* the reply exists. Script settles Japanese, Korean, Chinese
and Arabic outright; Latin-script languages are scored on function words,
diacritics and n-grams. It refuses to guess on thin evidence — "ok, thanks" must
not flip someone's interface.

## The AI

- **Reply language** is a rule, not a lookup: *"reply in the same language the
  customer writes in, matching their most recent message. Never answer in English
  just because these instructions are in English."* A detected locale is passed
  as a hint for the ambiguous opening message, never as a lock.
- A workspace that must answer in one fixed language sets
  `agent.settings.reply_language`.
- **Retrieval** prefers help-center material in the reader's language — a boost
  (`LOCALE_MATCH_BOOST`), never a filter. Most workspaces have an English-only
  knowledge base and international customers; excluding non-matching documents
  would answer "I don't know" to a question the KB answers perfectly well.
- Documents with no locale (crawled pages, uploads) are untouched, so a workspace
  that never translates anything sees no ranking change at all.

## Help centre

Articles and collections carry `locale` and `translation_key`. Slugs are unique
per `(workspace, locale)`, so `/de/passwort-zuruecksetzen` and
`/en/reset-password` coexist.

Fallback is **per translation group, not wholesale**: a workspace that has
translated three of its forty articles shows those three in German and the rest
in its default language — not a near-empty German help centre, and not the
English version of all forty.

## Writing translatable UI

```tsx
import { t, tParts } from '@/i18n'

<Button>{t('common.save')}</Button>
<p>{t('help.no_results', { query })}</p>
<span>{t('csat.star', { count: n })}</span>   // plural picked by the locale
```

For a sentence that wraps a value in markup, **do not** concatenate:

```tsx
// ✗ freezes English word order — Japanese and Turkish put the noun elsewhere
<span>The assistant wants to <strong>{name}</strong></span>

// ✓ the translation decides where the element goes
const [before, after] = tParts('action.wants_to', 'action')
<span>{before}<strong>{name}</strong>{after}</span>
```

Dates and numbers come from `@/lib/format`, which follows the *app's* language
rather than the browser's. Those disagree the moment someone picks a language in
settings, and "1,234.5" inside an otherwise German page is a bug people notice.

RTL: the widget stylesheet uses logical properties (`margin-inline-start`, not
`margin-left`) and both surfaces set `dir` from the active locale.

## The guard

`make i18n-check` (wired into `make lint`, so `make verify` runs it) fails on:

- a key English defines that a locale is missing, **beyond that set's coverage floor**;
- a plural form the locale's own CLDR rules can produce but the catalog lacks —
  a Polish catalog with only `_one`/`_other` renders "5 gwiazdki" instead of
  "5 gwiazdek";
- a translation interpolating a `{{variable}}` English does not provide, which
  would render as literal braces in production;
- keys English has dropped;
- drift between the locale registry copies each runtime keeps.

Translations arrive as pull requests from people who cannot run the app in their
language, so the build has to be the reviewer.

## Coverage, honestly

```
backend    12/12 locales complete   (15 keys)
widget     12/12 locales complete   (99 keys)
dashboard   0/12 locales complete   (1,036 keys — 17% translated)
```

The **widget and backend are complete**: every string an end user or an email
recipient sees exists in all 13 languages.

The **dashboard is deliberately partial.** Its 1,036 keys were extracted by
codemod in one pass; translating all of them is ~12,000 entries and was scoped as
a follow-up wave. What is translated is the surface an agent sees constantly —
all 139 shared `common.*` strings, the entire auth flow, and relative-time
formatting. The remaining 859 keys fall back to English key by key, which is why
`t` falls back rather than rendering a key.

This is tracked rather than hidden: `minCoverage` in `scripts/check-i18n.mjs` is
a floor the build enforces, and the coverage table prints on every run. **Raise
the floor as waves land; never lower it.**

### Adding a translation wave

1. Translate more of `frontend/src/i18n/catalogs/en.json` into a locale file.
2. Run `make i18n-check` — it reports the new coverage.
3. Raise `minCoverage` for `dashboard` to the level now reached.

### Adding a locale

1. Add it to `backend/app/core/i18n.py` `LOCALES` **and** its plural rule to
   `plural_category`, plus the `PLURAL_CATEGORIES` test fixture.
2. Mirror it into `widget/src/i18n/locales.ts` and
   `frontend/src/i18n/locales.ts` (the guard fails if these drift).
3. Add `<locale>.json` to each catalog directory.
4. `make i18n-check`.

## Not yet localised

Stated plainly so it is not mistaken for done:

- **Chrome extension** (53 files) — agent-facing; the guard already has a slot
  for `extension/src/i18n/catalogs`.
- **Landing page and docs site** (Astro) — marketing content, which is a
  copywriting job more than an engineering one.
- **Dashboard strings inside JSX expressions** — the codemod deliberately skips
  anything with an interpolation (`{saving ? 'Saving…' : 'Save'}`), because a
  sentence assembled from an expression is safer converted by hand than by
  regex. These remain English and are found by grepping for string literals
  inside `.tsx` ternaries.
