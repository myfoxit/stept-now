# Internationalisation

Stept ships **5 languages**: English, German, French, Spanish and Italian —
completely, on every surface a user can reach.

That number went *down*. An earlier wave shipped thirteen languages whose
catalogs were mostly empty: the backend and widget were complete, the dashboard
was 17% translated, and the extension and marketing site were not localised at
all. Thirteen half-languages is worse than five whole ones — it puts a language
picker in front of someone, and then hands them an English screen. The set was
cut to the five we could finish, and the coverage floor was raised to 100% so it
stays that way.

Before any of this, the repo had no i18n of any kind — no library, no catalogs,
no locale column, no `Accept-Language` handling. `docs/CHATWOOT-BACKLOG.md` §2.6
had flagged the gap and recommended building the framework early, precisely
because retrofitting extraction across the test suite gets more expensive with
every wave.

---

## One format, five runtimes

The backend, the dashboard, the widget, the extension and the marketing site all
read the same catalog shape, so a string can move between surfaces without being
rewritten and one guard can police all of them.

```jsonc
{
  "inbox.reply_placeholder": "Write a reply…",     // flat dotted keys
  "csat.star_one": "{{count}} star",                // {{name}} interpolation
  "csat.star_other": "{{count}} stars"              // CLDR plural siblings
}
```

Flat keys beat nested ones for a file that is diffed and machine-checked: a
missing key is one missing line, not a collapsed subtree.

| Surface | Runtime | Catalogs |
| --- | --- | --- |
| Backend | `backend/app/core/i18n.py` | `backend/app/i18n/<locale>.json` |
| Dashboard | `frontend/src/i18n/` | `frontend/src/i18n/catalogs/<locale>.json` |
| Widget | `widget/src/i18n/` | `widget/public/i18n/<locale>.json` |
| Extension | `extension/src/i18n/` | `extension/src/i18n/catalogs/<locale>.json` |
| Landing | `landing/src/i18n/` | `landing/src/i18n/<locale>.json` |

Each browser runtime keeps its own copy of the locale registry (they are separate
bundles and must not import across package boundaries); the guard fails the build
if the copies drift.

### Why not i18next

i18next earns its ~40 KB on namespaces, pluggable backends and a plugin system.
What these surfaces need is lookup, interpolation and plurals — and
`Intl.PluralRules` supplies correct CLDR categories for free, so the browser
runtimes agree with the backend's hand-written rules without shipping a rules
table. The one real loss is `<Trans>`; `tParts` covers that case (below).

Python has no `Intl`, so `plural_category` implements CLDR for the five shipped
locales by hand. Adding a locale means adding its rule there *and* to the test
fixture — deliberate friction, because a locale whose plurals silently fall back
to English is worse than one we never shipped.

### How each surface loads a catalog

Same format, four different delivery constraints:

- **Widget** — English is inlined; the other four are static assets under
  `/widget-assets/i18n/`, fetched once when needed. The bundle runs on a
  customer's page, so shipping four unread catalogs to every visitor is rent we
  charge them.
- **Dashboard** — English is inlined; the rest are dynamic imports Vite
  code-splits per locale.
- **Extension** — every catalog is imported statically. They are small, and the
  code runs in three separate bundles (side panel, content scripts, service
  worker), so a shared async loader would buy nothing.
- **Landing** — resolved at build time. Astro emits a static page per locale, so
  no catalog reaches the browser at all.
- **Backend** — catalogs are read from disk at import.

## The rule that matters: the visitor's language wins

Most chat widgets read `navigator.language` and stop. That gets the common case
right and the interesting case wrong: someone on a borrowed laptop, a shared
kiosk, or a browser still on its factory `en-US` types a question in German and
gets answered in German — inside an English interface.

So the widget's strongest signal is **what the visitor actually writes**:

1. `learned` — the language detected from their own messages, stored on the
   contact. The only signal that is evidence about *this person*.
2. `explicit` — `SteptSettings.locale`, the host page's setting.
3. `navigator.languages`.
4. the workspace default.

```html
<script>
  window.SteptSettings = {
    workspaceKey: 'wk_…',
    locale: 'de',        // optional: a starting language
    lockLocale: true,    // optional: keep it even against what they write
  }
</script>
```

`lockLocale` exists for the regulated single-language product and the screenshot
harness. It is off by default, because a visitor writing German is better served
by a German interface than by the one the site owner assumed.

Detection lives in `backend/app/services/language.py` and is **not** an LLM call.
The model already mirrors the customer's language without being told which one it
is; what a model cannot do is tell the widget which language to render its
buttons in *before* the reply exists. Script settles Japanese, Korean, Chinese and
Arabic; Latin-script languages are scored on function words, diacritics and
n-grams. It refuses to guess on thin evidence — "ok, thanks" must not flip
someone's interface.

Its tables **deliberately cover more languages than we ship.** A language we can
recognise but not render still earns its keep as a *distractor*: Dutch text wins
the Dutch score and comes back `None`, instead of scraping past the threshold as
German. The filter against `SUPPORTED_LOCALES` happens once, at the very end —
everything upstream is pure recognition. So a visitor writing Japanese gets an
English interface (correct: we have no Japanese), not a wrong guess.

## The AI

- **Reply language** is a rule, not a lookup: *"reply in the same language the
  customer writes in, matching their most recent message. Never answer in English
  just because these instructions are in English."* A detected locale is passed
  as a hint for the ambiguous opening message, never as a lock. The model is free
  to answer in a language we have no catalog for — the *interface* is limited to
  five languages, the conversation is not.
- A workspace that must answer in one fixed language sets
  `agent.settings.reply_language`. **That setting is not restricted to the five
  shipped locales.** It resolves through `reply_language_name`, which knows ~60
  languages by name, not through `normalize_locale`, which only knows the ones we
  render. The distinction is load-bearing: routing it through the interface list
  meant a workspace that asked for Japanese replies had its configuration
  silently discarded and got whatever the customer happened to write. A tag we
  cannot name at all falls back to mirroring the customer, which is the safe
  answer — better than instructing a model to "always reply in xx".
- **Retrieval** prefers help-center material in the reader's language — a boost
  (`LOCALE_MATCH_BOOST`), never a filter. Most workspaces have an English-only
  knowledge base and international customers; excluding non-matching documents
  would answer "I don't know" to a question the KB answers perfectly well.
- Documents with no locale (crawled pages, uploads) are untouched, so a workspace
  that never translates anything sees no ranking change at all.

## Help centre

Articles and collections carry `locale` and `translation_key`. Slugs are unique
per `(workspace, locale)`, so `/de/passwort-zuruecksetzen` and
`/en/reset-password` coexist.

Fallback is **per translation group, not wholesale**: a workspace that has
translated three of its forty articles shows those three in German and the rest
in its default language — not a near-empty German help centre, and not the
English version of all forty.

Author locales are not limited to the five the interface ships. A workspace can
write articles in any language; the UI chrome around them is what has a catalog.

## The marketing site

`landing/` is Astro, so localisation happens at build time and costs the visitor
nothing:

- English stays at `/`; the others live under `/de/`, `/fr/`, `/es/`, `/it/`.
- Each page is a thin route that renders a shared component with a `locale` prop
  (`src/pages/index.astro` and `src/pages/[lang]/index.astro` both render
  `HomePage.astro`), so there is exactly one copy of the markup.
- `LangSwitcher.astro` maps the current path into each locale via `localePath` /
  `stripLocale`, so switching language keeps you on the page you were reading.
- `Layout.astro` emits `hreflang` alternates and a canonical URL per locale, and
  `sitemap.xml` lists every localized route.

## Writing translatable UI

```tsx
import { t, tParts } from '@/i18n'

<Button>{t('common.save')}</Button>
<p>{t('help.no_results', { query })}</p>
<span>{t('csat.star', { count: n })}</span>   // plural picked by the locale
```

For a sentence that wraps a value in markup, **do not** concatenate:

```tsx
// ✗ freezes English word order — German sends the verb to the end of the clause
<span>The assistant wants to <strong>{name}</strong></span>

// ✓ the translation decides where the element goes
const [before, after] = tParts('action.wants_to', 'action')
<span>{before}<strong>{name}</strong>{after}</span>
```

Dates and numbers come from `@/lib/format`, which follows the *app's* language
rather than the browser's. Those disagree the moment someone picks a language in
settings, and "1,234.5" inside an otherwise German page is a bug people notice.

RTL: no right-to-left locale ships today, but the machinery is intact — the
widget stylesheet uses logical properties (`margin-inline-start`, not
`margin-left`), `localeDirection` still resolves a direction, and both surfaces
set `dir` from the active locale. Adding Arabic or Hebrew is a catalog and a
registry entry, not a re-layout.

## The guard

`make i18n-check` (wired into `make lint`, so `make verify` runs it) fails on:

- a key English defines that a locale is missing — every set's floor is 100%;
- a plural form the locale's own CLDR rules can produce but the catalog lacks.
  All five shipped locales use only `one`/`other`, but the check is general, and
  it already matters: French groups 0 with 1, so a French `_one` has to read
  correctly for "0 message" too;
- a translation interpolating a `{{variable}}` English does not provide, which
  would render as literal braces in production;
- keys English has dropped (dead weight that survives refactors);
- drift between the locale registry copies each runtime keeps — including the
  landing's, so a locale can never exist in the product without a marketing page.

Translations arrive as pull requests from people who cannot run the app in their
language, so the build has to be the reviewer.

## Coverage

```
backend     4/4 locales complete   (21 keys)
widget      4/4 locales complete   (124 keys)
dashboard   4/4 locales complete   (1,076 keys)
extension   4/4 locales complete   (205 keys)
landing     4/4 locales complete   (157 keys)
```

Complete means complete: every string in the product, the messenger, the
extension side panel, the transactional emails and the marketing site exists in
all five languages. `make i18n-check` prints this table on every run, and the
floor is 100% for every set — so the table cannot quietly rot.

`t` still falls back to English key by key. That is a safety net for a
half-loaded chunk or a failed catalog fetch, not a translation strategy.

### Adding a translation wave

There is no such thing any more. The floor is 100%, so a locale is either
finished or not shipped. **Never lower a floor to make a change pass** — finish
the strings, or remove the locale from the registry.

Adding new English strings is the normal case: add them to `en.json`, and
`make i18n-check` will fail until every locale has them. That failure is the
feature.

### Adding a locale

1. Add it to `backend/app/core/i18n.py` `LOCALES` **and** its plural rule to
   `plural_category`, plus the `PLURAL_CATEGORIES` test fixture.
2. Mirror it into `widget/src/i18n/locales.ts`, `frontend/src/i18n/locales.ts`,
   `extension/src/i18n/locales.ts` and `landing/src/i18n/index.ts` (the guard
   fails if these drift).
3. Add `<locale>.json` to all five catalog directories — complete, because the
   floor is 100%.
4. If it is RTL, set `dir: 'rtl'` in the registry entries and check the widget in
   a mirrored layout.
5. `make i18n-check`.

### Removing a locale

The reverse, and a legitimate move: delete its catalogs, its registry entries and
its plural rule. A locale nobody maintains is a promise the product stops
keeping.

## Not localised, by choice

Stated plainly so it is not mistaken for done:

- **Docs site** (`docs-site/`, Astro) — developer documentation, English only.
  Localising reference docs that change every week is a treadmill, and the
  audience reads English.

## The extraction gap, measured

Coverage above is a *translation* number: every key English defines exists in all
five languages. A separate thing can still be wrong — a string that was never
turned into a key at all, and so renders English no matter the locale. The two
are easy to confuse, so the second is measured here rather than described.

The original codemod deliberately skipped anything assembled inside a JSX
expression (`{saving ? 'Saving…' : 'Save'}`), because a sentence built from an
expression is safer converted by hand than by regex. What remains:

```
~60 ternary label pairs + a handful of hardcoded props, across 44 .tsx files
```

The **auth flow is fully extracted** (it is the first screen anyone sees, so it
was finished first: subtitles, submit-button states, zod validation messages,
OAuth failures and toast fallbacks are all keys now). The rest is spread thin
across feature dialogs.

Two shapes of defect were found and fixed while doing it, both worth recognising
because the guard cannot see either:

1. **Spliced fragments.** A translated fragment concatenated with hardcoded
   English — `{t('settings.connection_settings_for_this')} <span>{channel}</span>
   channel. Secrets are stored encrypted…`. Coverage reads 100%, and the sentence
   still renders half-English in every locale, with English word order frozen in.
   The fix is one key for the whole sentence plus `tParts`. Three of these
   existed.
2. **Extraction into a comment.** The codemod rewrote the inside of a `//`
   comment, leaving a catalog key that nothing renders and a mangled comment.

When adding a key for a sentence that wraps a value in markup, use `tParts`. When
you find a fragment key whose English value does not end in punctuation, suspect
the first defect and check its call site.

Note that a zod schema is a module-level constant, evaluated at import: calling
`t()` there freezes whichever language was active first. The auth forms build
their schema inside the component instead (`useMemo(makeSchema, [])`) — do the
same for any new validated form.
