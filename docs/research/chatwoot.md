# Chatwoot Architecture Research (for Stept)

Source: shallow clone of github.com/chatwoot/chatwoot @ `beffabee` (2026-07-30), Rails 7.1, Postgres + pgvector.
All paths relative to the Chatwoot repo root. Schema facts from `db/schema.rb` (version 2026_07_29).

## 1. Architecture map

| Dir | Purpose |
|---|---|
| `db/schema.rb` | Single source of truth; pg extensions: `pgcrypto`, `pg_trgm`, `vector`, `pg_stat_statements` |
| `app/models` | AR models incl. `channel/*` (one model+table per channel type), `concerns/*` (assignment, labelable, reportable) |
| `app/services` | Plain-Ruby service objects: `auto_assignment/`, `automation_rules/`, `conversations/`, `widget/`, `email/`, per-provider dirs |
| `app/listeners` | Pub/sub consumers of a central event dispatcher: `webhook_listener`, `reporting_event_listener`, `agent_bot_listener`, `automation_rule_listener`, `notification_listener`, `csat_survey_listener`, `campaign_listener`, `action_cable_listener` |
| `app/dispatchers` | `Rails.configuration.dispatcher.dispatch(EVENT, time, payload)` — sync + async (Sidekiq) fan-out to listeners |
| `app/mailboxes` | ActionMailbox inbound email pipeline (`application_mailbox.rb`, `reply_mailbox.rb`) |
| `app/builders` | Multi-model creation (`ContactInboxWithContactBuilder`, message builders) |
| `app/controllers/api/v1/widget` | Widget REST API (contact-JWT auth); `public/api/v1/` = API-channel + help-center public endpoints |
| `app/javascript/sdk` | Embed loader (`sdk.js`, `IFrameHelper.js`) — bubble + iframe, postMessage bridge |
| `app/javascript/widget` | Vue app rendered inside the iframe |
| `app/jobs` | Sidekiq jobs (`WebhookJob`, `SendReplyJob`, `AutoAssignment::AssignmentJob`) |
| `enterprise/` | Paid features layered via `prepend_mod_with`/`include_mod_with` module injection (SLA, Captain AI, audit) |
| `lib/` | Framework-ish code; `config/routes.rb` has public help-center routes (`hc/:slug/...`) |

Core pattern: **models emit domain events after commit → dispatcher → listeners → jobs**. Every side-effect (webhooks, reports, bots, notifications, websockets, automation) is a listener, not inline controller code.

## 2. Data model (db/schema.rb)

Conventions worth copying: every tenant table carries a denormalized `account_id` (even when reachable via parent) for cheap scoping/indexing; jsonb catch-alls `additional_attributes` (system-set) vs `custom_attributes` (user-defined) on account/contact/conversation; enums stored as integers; `display_id` per-account monotonic via a Postgres trigger + per-account sequence (`conv_dpid_seq_<account_id>`, schema.rb:1536).

### Tenancy & users
- **accounts**: `name`, `locale`(int), `domain`, `support_email`, `feature_flags`(bigint bitfield + `feature_flags_ext_1`), `auto_resolve_duration`, `limits` jsonb, `custom_attributes` jsonb, `status`(int active/suspended), `settings` jsonb, `internal_attributes` jsonb.
- **users**: Devise fields, `name`, `display_name`, `email`, `pubsub_token`(uniq, per-user websocket auth), `availability`(int), `ui_settings` jsonb, `custom_attributes` jsonb, `type`(STI → SuperAdmin), `message_signature`, OTP/2FA columns.
- **account_users** (membership join): `account_id`+`user_id` uniq, `role`(int enum: agent 0/administrator 1), `inviter_id`, `active_at`, `availability`(int per-account!), `auto_offline` bool, `custom_role_id` (enterprise granular perms: `custom_roles.permissions text[]`), `agent_capacity_policy_id`. Availability is **per account**, not global — key design point.
- **access_tokens**: polymorphic `owner_type/owner_id` (User or AgentBot), `token` uniq — single API-token mechanism for humans and bots.

### Inboxes & channels (polymorphic)
- **inboxes**: `channel_id` + `channel_type` (polymorphic → concrete `channel_*` table), `account_id`, `name`, `enable_auto_assignment`, `auto_assignment_config` jsonb (e.g. max_assignment_limit), `greeting_enabled/greeting_message`, `email_address`, `working_hours_enabled`, `out_of_office_message`, `timezone`, `enable_email_collect`, `csat_survey_enabled` + `csat_config` jsonb, `allow_messages_after_resolved`, `lock_to_single_conversation`, `portal_id`, `sender_name_type` + `business_name`.
- **inbox_members**: `inbox_id`+`user_id` uniq — agent pool per inbox.
- Channel tables each hold only provider-specific config; shared behavior via `Channelable` concern (`app/models/concerns/channelable.rb`: `has_one :inbox, as: :channel`):
  - **channel_web_widgets**: `website_token`(uniq, public identifier), `hmac_token`(uniq, secret for identity verification), `hmac_mandatory`, `widget_color`, `welcome_title/tagline`, `reply_time`(enum), `feature_flags`(int bitfield: attachments/emoji/end-conversation…), `pre_chat_form_enabled` + `pre_chat_form_options` jsonb (`pre_chat_message`, `pre_chat_fields:[{field_type:standard|custom,name,label,type,required,enabled,regex_pattern,…}]`), `continuity_via_email`, `allowed_domains` (CSV → CSP frame-ancestors in `widgets_controller.rb`).
  - **channel_api**: `identifier`(uniq), `hmac_token`(uniq), `hmac_mandatory`, `webhook_url` (per-inbox push of events to the integrator), `additional_attributes` jsonb.
  - **channel_email**: `email`(uniq), `forward_to_email`(uniq generated forwarding addr), full IMAP+SMTP cred columns, `provider` + `provider_config` jsonb (Microsoft/Google OAuth), `verified_for_sending`.
  - **channel_whatsapp**: `phone_number` uniq, `provider`+`provider_config`, `message_templates` jsonb cache + `message_templates_last_updated`, health-check cols. Twilio/SMS/Telegram/Line/Instagram/FB/TikTok similar minimal cred tables.
- **contact_inboxes** (identity of a contact *on one channel*): `contact_id`, `inbox_id`, `source_id` (email addr / phone / widget UUID / external id) with `inbox_id+source_id` uniq, `hmac_verified` bool, `pubsub_token`(uniq — websocket auth for the widget visitor). Conversations hang off `contact_inbox_id`.

### Contacts & companies
- **contacts**: `name/middle_name/last_name`, `email`, `phone_number`, `identifier` (external user id), `account_id`, `additional_attributes` jsonb (browser, referer, ip…), `custom_attributes` jsonb, `last_activity_at`, `contact_type`(int: visitor 0/lead/customer), `location`, `country_code`, `blocked` bool, `company_id`. Uniques per account on email, identifier; gin trgm index on name/email/phone/identifier for search; partial index "resolved contacts" where email/phone/identifier non-empty.
- **companies**: `name`, `domain` (uniq per account), `contacts_count`, jsonb attrs. **notes**: contact-level notes (separate from conversation private notes).

### Conversations
- **conversations**: `account_id`, `inbox_id`, `contact_id`, `contact_inbox_id`, `status` int enum **{open:0, resolved:1, pending:2, snoozed:3}**, `priority` int enum {low/medium/high/urgent}, `assignee_id` (User) + `assignee_agent_bot_id` (mutually exclusive; virtual polymorphic assignee), `team_id`, `campaign_id`, `display_id` (per-account trigger), `uuid` (gen_random_uuid, public), `identifier`, `additional_attributes` jsonb, `custom_attributes` jsonb, `snoozed_until`, `status_changed_at`, `sla_policy_id`, `cached_label_list` text (denormalized CSV of labels!), and the four timestamp trackers:
  - `contact_last_seen_at` / `agent_last_seen_at` / `assignee_last_seen_at` → unread computed as count of incoming messages with `created_at > agent_last_seen_at` (`Conversation.unread_messages_condition`), **no unread counter column**.
  - `first_reply_created_at` → set once on first human reply (FRT metric).
  - `waiting_since` → set on creation and on each incoming msg if blank; cleared on human/bot reply and on resolve ("needs response" queue + reply_time metric).
  - `last_activity_at` → bumped via `update_columns` on every message (list sort key).
- Hot composite index: `(account_id, inbox_id, status, assignee_id)`; uniq `(account_id, display_id)`.
- **conversation_participants**: `user_id`+`conversation_id` uniq (watchers, drive notifications). **mentions**: `user_id`+`conversation_id`+`mentioned_at`.
- **teams**: `name` uniq/account, `allow_auto_assign`, icon; **team_members** join.
- **labels**: `title` uniq/account, `color`, `show_on_sidebar`, `description`; applied via acts-as-taggable **tags/taggings** (polymorphic `taggable`, global `tags.name` uniq, `taggings_count` counter) — labels metadata and tag strings are only loosely linked by title.
- **csat_survey_responses**: `conversation_id`, `message_id`(uniq — the survey template message), `rating` int, `feedback_message`, `contact_id`, `assigned_agent_id`, review-notes columns.
- **canned_responses**: `account_id`, `short_code`, `content` — trivially simple.

### Messages
- **messages**: `content` text (150k cap), `processed_message_content` (email-stripped/plain version), `account_id`, `inbox_id`, `conversation_id` (all denormalized), `message_type` int enum **{incoming:0, outgoing:1, activity:2, template:3}**, `private` bool (internal note), `status` int enum {sent, delivered, read, failed}, `source_id` text (external/provider message id; email Message-ID; dedupe key), `content_type` int enum **{text, input_text, input_textarea, input_email, input_select, cards, form, article, incoming_email, input_csat, integrations, sticker, voice_call}**, `content_attributes` json (typed payload: `submitted_email, items, submitted_values, email:{html_content,text_content,quoted}, in_reply_to, in_reply_to_external_id, deleted, external_created_at, external_error, translations, data, automation_rule_id, external_echo`), `sender_type/sender_id` **polymorphic (User | Contact | AgentBot | Captain::Assistant)**, `external_source_ids` jsonb (e.g. slack ts), `additional_attributes` jsonb (campaign_id, template_params), `sentiment` jsonb. Gin trgm on content; composite `(conversation_id, account_id, message_type, created_at)`.
- **attachments**: own table (not just ActiveStorage): `file_type` int (image/audio/video/file/location/fallback/contact), `external_url`, `coordinates_lat/long`, `fallback_title`, `extension`, `meta` jsonb (transcriptions) + ActiveStorage blob for the binary. Max 15/message.

### Automation / macros / campaigns
- **automation_rules**: `event_name` string (conversation_created / conversation_updated / message_created / conversation_opened…), `conditions` jsonb, `actions` jsonb, `active`, `execution_delay` int minutes (10..43200) — delayed rules materialize into **automation_rule_pending_executions** (`due_at`, `episode_key` uniq per rule+conversation+episode, `status`, `skip_reason`) and are re-validated at fire time; changing a rule discards armed rows.
  - Condition row shape (spec/factories/automation_rules.rb): `{"attribute_key":"status","filter_operator":"equal_to","values":["resolved"],"query_operator":"AND"|nil,"custom_attribute_type":...}` — flat array, operators chained AND/OR; supported keys incl. content, email, country_code, status, message_type, browser_language, assignee_id, team_id, inbox_id, priority, labels, private_note + custom attributes; filter_operators incl. equal_to/not_equal_to/contains/attribute_changed etc. (`app/models/automation_rule.rb`).
  - Action row shape: `{"action_name":"assign_team","action_params":[1]}`; params can be array of ids, strings (labels), or object (`send_email_to_team: {message, team_ids}`); action vocabulary: send_message, add/remove_label, assign_team/agent, remove_assigned_*, send_email_to_team, send_webhook_event, mute, send_attachment, change_status/resolve/open/pending/snooze, change_priority, send_email_transcript, add_private_note.
- **macros**: same `actions` jsonb vocabulary, manually triggered, `visibility` enum {personal, global}, created_by/updated_by (`app/models/macro.rb`).
- **campaigns**: `display_id` (trigger-seq), `campaign_type` int {ongoing (widget proactive) / one_off (SMS blast)}, `campaign_status`, `message`, `sender_id`, `inbox_id`, `trigger_rules` jsonb (`{url, time_on_page}`), `audience` jsonb (label ids), `scheduled_at`, `trigger_only_during_business_hours`, `template_params` jsonb.
- **custom_attribute_definitions**: `attribute_key` + `attribute_model` int {conversation_attribute:0, contact_attribute:1} uniq/account, `attribute_display_type` int (text/number/date/list/checkbox/link), `attribute_values` jsonb (list options), `regex_pattern/regex_cue` — values live in the parent row's `custom_attributes` jsonb.
- **custom_filters**: saved segments — `filter_type`, `query` jsonb.

### Reporting / SLA
- **reporting_events**: append-only metric rows — `name` (string: conversation_resolved / first_response / reply_time / conversation_opened / conversation_bot_resolved / conversation_bot_handoff), `value` float (seconds), `value_in_business_hours` float, `account_id/inbox_id/user_id/conversation_id`, `event_start_time/event_end_time`. Index `(account_id, name, created_at)`.
- **reporting_events_rollups**: pre-aggregated `(account_id, date, dimension_type, dimension_id, metric)` uniq → `count`, `sum_value`, `sum_value_business_hours` — written synchronously alongside each raw event (`ReportingEvents::RollupService`, best-effort with rebuild path).
- **sla_policies** (`first_response_time_threshold`, `next_response_time_threshold`, `resolution_time_threshold` floats, `only_during_business_hours`) + **applied_slas** (per conversation, `sla_status`) + **sla_events** (misses: `event_type`, `meta`).
- **working_hours**: per inbox, `day_of_week`, open/close hour+minute, `closed_all_day`, `open_all_day` — used for business-hours math in reporting (`lib/reporting_event_helper` via listener).

### Webhooks / notifications / bots / portal
- **webhooks**: `account_id`, `inbox_id`, `url` (uniq/account), `webhook_type` int {account, inbox}, `subscriptions` jsonb array (default: conversation_status_changed, conversation_updated, conversation_created, contact_created, contact_updated, message_created, message_updated, webwidget_triggered), `secret` (HMAC signing), `name`.
- **notifications**: `notification_type` int, polymorphic `primary_actor` (the conversation/message) + `secondary_actor`, `read_at`, `snoozed_until`, `last_activity_at`, `meta` jsonb. **notification_settings**: per user+account, `email_flags`/`push_flags` int bitfields. **notification_subscriptions**: browser-push/FCM device rows.
- **agent_bots**: `name`, `outgoing_url` (webhook target), `bot_type` int {webhook:0}, `bot_config` jsonb, `secret`, nullable `account_id` (global bots); **agent_bot_inboxes** join with `status` (active/inactive) wires a bot to an inbox. Bot acts back via REST using its `access_token` (polymorphic owner).
- **portals** (help center): `slug` uniq global, `custom_domain` uniq, `config` jsonb {allowed_locales}, `channel_web_widget_id` (widget↔KB link), `archived`, ssl_settings; **portals_members** (editors). **categories**: per portal+locale, `slug` uniq per (portal, locale), `parent_category_id` (tree), `associated_category_id` (cross-locale linking), icon. **articles**: `portal_id`, `category_id`, `title/description/content`, `status` int {draft/published/archived}, `views`, `author_id`, `slug` uniq, `position`, `locale`, `associated_article_id` (translation link), `meta` jsonb, `draft_title/draft_content` (draft-vs-published in same row). **article_embeddings**: pgvector(1536) per term chunk, ivfflat index.
- **Captain (AI agent, enterprise tables in OSS schema)**: `captain_assistants` (`config` jsonb, `response_guidelines` jsonb[], `guardrails` jsonb[]), `captain_documents` (crawled KB, sync status), `captain_assistant_responses` (Q/A memory + embedding 1536), `captain_scenarios` (`instruction`, `tools` jsonb — agent skills), `captain_custom_tools` (**HTTP tool calling**: `slug`, `http_method`, `endpoint_url`, `request_template`, `response_template`, `auth_type`+`auth_config` jsonb, `param_schema` jsonb[]), `captain_inboxes` join, `agent_sessions` (per-run telemetry: `llm_model`, `credits_consumed`, faq/document/scenario id arrays, `run_context` jsonb), `copilot_threads`/`copilot_messages` (agent-side AI chat, message jsonb).

## 3. Key flows

**Conversation lifecycle** (`app/models/conversation.rb`)
- Status machine {open, resolved, pending, snoozed} is plain enum + callbacks (they left a `FIXME: implement state machine`). `snoozed_until` auto-cleared unless snoozed; `status_changed_at` set on change; resolve clears `waiting_since` via `update_column`.
- Creation: contact blocked → resolved; inbox has active bot (or bot campaign) → **pending** + `assignee_agent_bot` set; else open. `waiting_since = created_at`; `display_id`/`uuid` come from DB trigger, reloaded post-commit.
- Incoming message reopens: snoozed → open; resolved → pending if bot inbox else open (`Message#reopen_conversation`). Bot handoff (`bot_handoff!`): clears bot assignee, opens, sets `waiting_since`, emits `CONVERSATION_BOT_HANDOFF`.
- Assignment: `AssignmentHandler` keeps assignee within team on team change; `AutoAssignmentHandler#run_auto_assignment` fires when status→open and assignee blank: legacy path = `AutoAssignment::AgentAssignmentService` → intersect(online agents from Redis presence, inbox members with capacity) → `InboxRoundRobinService` (Redis list per inbox, pop-push rotation, self-healing vs member list); V2 = debounced per-inbox `AssignmentJob` with `assignment_policies` (assignment_order round_robin/balanced, fair_distribution_limit/window) + `agent_capacity_policies` with per-inbox `inbox_capacity_limits.conversation_limit`.
- Events on every mutation via `dispatcher_dispatch`: CONVERSATION_CREATED/OPENED/RESOLVED/STATUS_CHANGED/READ/CONTACT_CHANGED/UPDATED with `previous_changes` payload.

**Message → side-effects** (`app/models/message.rb` after_create_commit chain): reopen conversation → set `last_activity_at` → dispatch MESSAGE_CREATED (+ FIRST_REPLY_CREATED once, using `valid_first_reply?` which excludes bots/campaigns/private) or update `waiting_since` → enqueue `SendReplyJob` (delivers to the channel provider) → `MessageTemplates::HookExecutionService` (greeting, email-collect prompt, CSAT template on resolve) → bump contact `last_activity_at`. Message-flood guard: ≥N msgs/minute per conversation → validation error (breaks automation loops).

**Inbound email** (`app/mailboxes/`): ActionMailbox ingress → `ApplicationMailbox` routes to `ReplyMailbox` if to-address matches `reply+<conversation-uuid>@domain` or `EmailChannelFinder` matches a channel address; `Mailbox::ConversationFinder` strategy chain: ReceiverUuid → InReplyTo header → References header → NewConversation. Whole persist wrapped in one transaction; message deduped by `source_id == Message-ID`; `MailPresenter` extracts reply-vs-quoted html/text into `content_attributes[:email]`; inline images re-hosted and substituted; contact created from sender via `ContactInboxWithContactBuilder` (source_id = email address).

**Widget boot & auth** (`app/javascript/sdk/*`, `app/controllers/widgets_controller.rb`, `api/v1/widget/*`): embed script loads `sdk.js` with `websiteToken`, injects bubble + iframe → iframe GET carries `website_token` + `cw_conversation` (JWT from localStorage/cookie). Server decodes JWT (`Widget::TokenService`, HS256, payload `{source_id, inbox_id}`, 180-day exp) → finds `ContactInbox` by `source_id`, else creates an anonymous contact+contact_inbox and issues a fresh JWT. All widget API calls send the JWT as `X-Auth-Token` (`WebsiteTokenHelper`). Realtime via `contact_inbox.pubsub_token` ActionCable channel. Identity: `setUser(identifier, {identifier_hash})` → `contacts_controller#set_user` recomputes `HMAC-SHA256(hmac_token, identifier)` with constant-time compare, marks `contact_inbox.hmac_verified=true`; if identifier changed, builds a *new* contact_inbox + token (session isolation). `hmac_mandatory` enforces it. Verified sessions only see conversations from verified contact_inboxes (`widget/base_controller#conversations`). Pre-chat form config is served from channel jsonb; campaigns fetched by SDK, `trigger_rules` {url,time_on_page} evaluated client-side, firing `webwidget_triggered` event.

**Automation execution** (`app/listeners/automation_rule_listener.rb`, `app/services/automation_rules/*`): dispatcher event → listener selects account's active rules for `event_name` → `ConditionsFilterService` compiles the conditions array into a scoped SQL query / in-memory check (custom attributes handled via jsonb) → `ActionService` executes each action (methods map 1:1 to action_name; messages created with `content_attributes.automation_rule_id` so they don't count as human replies). Delayed rules insert `automation_rule_pending_executions` keyed by `episode_key` (e.g. status_changed_at) and a sweeper re-validates conditions at `due_at`.

**Reporting emission** (`app/listeners/reporting_event_listener.rb`): CONVERSATION_RESOLVED → row `conversation_resolved` value=resolve_time(s) (+ `conversation_bot_resolved` twin if bot inbox and no human outgoing msg); FIRST_REPLY_CREATED → `first_response` (start = last non-human activity, not created_at); REPLY_CREATED (carries the old `waiting_since`) → `reply_time`; CONVERSATION_OPENED → reopen gap since last resolved event; bot handoff → `conversation_bot_handoff` (deduped per conversation). Each write also updates the daily rollup table; business-hours variant computed from inbox `working_hours`.

**Webhook delivery** (`app/listeners/webhook_listener.rb`): payload = `<entity>.webhook_data` merged with `{event, changed_attributes}`; account-level webhooks filtered by `subscriptions` array; API-channel inboxes additionally push every event to `channel_api.webhook_url`. Delivery = `WebhookJob.perform_later(url, payload, type, secret:, delivery_id: uuid)` (signed, async, retried). Agent bots are the identical mechanism aimed at `agent_bots.outgoing_url` (`agent_bot_listener.rb`); the bot replies by calling the REST API with its access token and flips the conversation open via `bot_handoff`.

**Help center**: public routes `hc/:slug/:locale/...` (config/routes.rb:623-634) — portal/category/article by slug, per-locale, search endpoint, sitemap, article tracking pixel, and `.md` endpoint (LLM-friendly). Articles have draft columns + status; embeddings table powers semantic search & AI answers.

## 4. Patterns to adopt for Stept

- **contact_inboxes as channel identity**: 3-way (contact, inbox, source_id uniq per inbox) + `hmac_verified` + per-session `pubsub_token`. This one table cleanly solves multi-channel identity, widget session auth, and identity merging. Direct port to Postgres/FastAPI.
- **Polymorphic channel → uniform inbox**: `inboxes(channel_type, channel_id)` + per-channel config table. In Stept: `inboxes` + `channel_kind` discriminator with per-kind config table (or single jsonb config table per kind) — keeps conversation/message logic 100% channel-agnostic; only "SendReplyJob" dispatches per kind.
- **Message quad enum**: `message_type {incoming, outgoing, activity, template}` + `private` bool + `status {sent,delivered,read,failed}` + `content_type` + `content_attributes` JSON. Activity-as-message gives a free audit timeline; `content_type/content_attributes` gives structured messages (forms, cards, article suggestions, CSAT) without schema churn.
- **Seen-timestamps not unread counters**: `agent_last_seen_at` / `contact_last_seen_at` on the conversation; unread = count(incoming where created_at > seen). Zero counter-drift.
- **`waiting_since` + `first_reply_created_at` + `last_activity_at` + `status_changed_at`** on conversations — four columns power the "needs response" queue, FRT/reply-time metrics, sorting, and SLA. Set/clear rules: see §3.
- **Event dispatcher + listeners**: single internal event bus (in Stept: in-process event emit → task queue) where webhooks, reporting, bots, automation, websocket pushes are all subscribers. Payload always includes `previous_changes` (changed_attributes) — webhook consumers love this.
- **reporting_events append-only + daily rollup table**, with `value` and `value_in_business_hours` computed at emission time from inbox working_hours. Metrics become `SUM/AVG WHERE name=X` — no fact-table joins.
- **Automation JSON schemas** (flat, validated against allow-lists):
  `conditions: [{attribute_key, filter_operator, values[], query_operator}]`, `actions: [{action_name, action_params}]`. Reuse the identical action vocabulary/executor for macros (manual) and automation (event-driven) — Chatwoot literally shares it.
- **Webhook rows with `subscriptions` jsonb + `secret` + delivery_id per attempt**; agent-bot = webhook out + REST in with bot-owned access token and `pending` conversation status + explicit `bot_handoff` transition. This is exactly the approval-gate seam Stept's agent engine needs: bot owns `pending`, humans own `open`.
- **Widget auth**: public `website_token` + contact JWT (`{source_id, inbox_id}`, long exp) in localStorage, `X-Auth-Token` header, optional `identifier_hash = HMAC_SHA256(secret, identifier)` with `hmac_mandatory` flag, constant-time compare, and *new contact on identifier change*. Also: `allowed_domains` → CSP frame-ancestors.
- **Per-account human-friendly ids** (`display_id`) via per-tenant sequence + insert trigger; keep global `uuid` for public URLs (CSAT survey link uses it).
- **Custom attributes**: definitions table (key, model, display_type, options, regex) + values in jsonb on the record; same mechanism reused by automation conditions and filters.
- **Portal model**: slug+locale scoped categories/articles, `associated_article_id` for translations, draft columns beside published content, `.md` public endpoint + embeddings table — directly reusable for Stept's RAG (articles are first-class RAG sources).
- **Captain's tool tables** as blueprint for Stept agent tools: `param_schema` jsonb, request/response templates, auth_config — plus `agent_sessions` for per-run cost/context telemetry.

## 5. Pitfalls / anti-patterns to avoid

- **No real state machine**: status transitions are scattered across callbacks (`toggle_status`, `Message#reopen_conversation`, `bot_handoff!`) — their own `FIXME` admits it. Stept: explicit transition function with guard table from day one.
- **Callback-soup on models**: Conversation/Message models carry enormous after_commit chains (assignment, activities, events, rollups). Hard to reason about ordering (they even cite a Rails callback-order bug). Stept: do side-effects in an application-service layer, not ORM hooks.
- **acts-as-taggable labels**: global `tags` table + string-matching to per-account `labels` metadata + denormalized `cached_label_list` CSV on conversations = three representations of one fact. Use a plain `conversation_labels(conversation_id, label_id)` join.
- **`account_id` nullable / uneven**: some tables (`webhooks.account_id`, `contact_inboxes`) lack NOT NULL or FK constraints; almost no DB-level FKs at all (only 4 `add_foreign_key` lines for 90+ tables) — integrity enforced only in app code. Stept: real FKs + NOT NULL tenant columns.
- **Availability state split** between Redis (OnlineStatusTracker), `users.availability`, and `account_users.availability` — subtle bugs; keep presence in one place with a documented precedence.
- **Round robin in Redis** list that must be re-synced against inbox_members (self-healing `validate_queue?`) — a fairness-window SQL query (their own V2 `assignment_policies`) is simpler and auditable; skip the Redis-queue stage entirely.
- **Email credentials in plaintext columns** (`channel_email.imap_password/smtp_password`); encrypt secrets at rest.
- **Enum-as-integer sprawl** without CHECK constraints (`status`, `content_type`, `attribute_display_type`) — meaningless ints in the DB; Stept: Postgres enums or text + CHECK.
- **JSON columns defaulting to `"{}"` string** (automation_rules.conditions default is the *string* `'"{}"'` — visible in schema) — validate/normalize JSON defaults.
- **Rollup written synchronously with rescue-swallow** (`safe_rollup`) — acknowledged possibility of under-counted rollups on retry; prefer idempotent upsert keyed by event id or async projection.
- **Message dedupe only by `source_id` lookup** (no unique index on `(conversation_id, source_id)`) — race-prone; enforce with a partial unique index.
- **Widget JWT lives 180 days in localStorage** with no rotation/refresh — fine for anonymous chat, but pair HMAC-verified sessions with shorter expiry.

## 6. Top 10 actionable recommendations for Stept

1. Copy the core entity graph verbatim: accounts → account_users(role, per-account availability) → inboxes(polymorphic channel) → conversations → messages, with contacts + contact_inboxes(source_id, hmac_verified, pubsub_token) as the identity spine.
2. Conversations table: adopt `status {open,pending,snoozed,resolved}` + `snoozed_until` + `waiting_since` + `first_reply_created_at` + `last_activity_at` + `status_changed_at` + `contact/agent_last_seen_at` + per-account `display_id` + public `uuid` — this exact column set powers inbox UX, SLAs, and reporting; implement transitions as one explicit state machine.
3. Messages: `message_type` + `private` + `content_type` + `content_attributes` (typed JSON per content_type, incl. `automation_rule_id` / `campaign_id` markers so bot/automation output never counts as human first-reply) + provider `source_id` with a unique dedupe index + separate attachments table with `file_type` and `meta`.
4. Build the internal event bus first (conversation.created/updated with changed_attributes, message.created, first_reply, reply with old waiting_since, status events); make webhooks, reporting, notifications, automation, agent-bot dispatch and websocket pushes all subscribers.
5. Reporting = append-only `reporting_events(name, value, value_in_business_hours, account/inbox/user/conversation, start, end)` + daily rollup upsert; compute business-hours values at emission from per-inbox working_hours rows.
6. Automation/macros: one shared action executor with `[{action_name, action_params}]`, conditions `[{attribute_key, filter_operator, values, query_operator}]` validated against allow-lists + custom-attribute definitions; add Chatwoot's newer `execution_delay` + pending-executions/episode design for time-based rules.
7. Widget: `website_token` (public) + long-lived contact JWT (`source_id`) + optional HMAC identity (`hmac_token` secret, `identifier_hash`, `hmac_mandatory`, new-contact-on-identifier-change, verified-scoped conversation history) + `allowed_domains` → frame-ancestors CSP + pre-chat form as jsonb field definitions + campaigns with client-evaluated `trigger_rules`.
8. Agent/bot integration seam: conversations owned by a bot sit in `pending` with `assignee_agent_bot_id`; external bots receive the same signed webhook payloads and reply via REST tokens; `bot_handoff` = open + clear bot + start waiting_since. Map Stept's approval gates onto pending→open.
9. Email channel: forwarding-address + `reply+<uuid>@domain`, conversation resolution strategy chain (uuid → In-Reply-To → References → new), Message-ID as source_id dedupe, reply/quoted split stored in content_attributes, single-transaction ingest.
10. Help center: portal(slug, custom_domain, locales jsonb) → categories(slug per locale, parent, translation link) → articles(draft columns, status, position, views, translation link, meta) + per-article embeddings (pgvector) and public `.md` endpoints — design articles as first-class RAG documents from day one.
