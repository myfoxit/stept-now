## Fixed in this pass

### BR-1 — the extension went offline until manually reloaded ✅

Chrome tears down an idle MV3 service worker, and the keepalive alarm is the **only** thing that
can revive it — `RunClient`'s 3s reconnect is a `setTimeout` that dies with the worker. The
alarm's own `onAlarm` listener decided whether to stay armed by reading module state that
`restore()` had not rehydrated yet. When the alarm was itself what revived the worker, it saw a
blank module (no `session`, no `runClient`, every flag false) and called
`chrome.alarms.clear(KEEPALIVE_ALARM)` on itself. Survival then depended on whether
`armKeepalive()` (inside `startRunClient`'s `ensureDeviceId().then(...)`) re-armed before or
after that clear landed — a race, which is why it only failed sometimes.

- **Fix:** the listener awaits the restore promise before judging, and keys off the restored
  *session* rather than a `runClient` that is installed asynchronously. It also re-opens the
  socket itself when the worker was torn down mid-session.
- **Guard:** decision extracted to `extension/src/remote/keepalive.ts`, pinned by 8 unit tests.
- **Verified:** backend killed for 90s (worker torn down) → backend restored → extension
  reconnected on its own in **5s**, no manual reload.

### BR-2 — the bridge is blind to iframes (High)

With the messenger open and fully painted, `browser_snapshot` returned three host-page buttons
and nothing else; `browser_page_text` omitted every word of the messenger. Any iframed surface
is invisible — a customer's checkout, an embedded console, and Stept's own widget alike.

```
page_text: "Stept widget host … New invoice … Getting started0/3"
           (no "Hi! How can we help?", no "Send us a message")
```

**Fix:** walk same-origin child frames when building the snapshot and index their elements;
route acts to the owning frame.

### BR-3 — `find` and `snapshot` disagree (Medium)

The widget loader mounts its launcher in a shadow root. The snapshot sees it; `find` does not.

```
snapshot           → [1]<button name="Open chat">
find "Open chat"   → found: []
find "New invoice" → found: [{index: 0, …}]   (light DOM, matches)
```

**Fix:** have `find` query the same indexed tree the snapshot builds.

### TO-1 — agent-driven tour plays are invisible to analytics (High)

`browser_run_tour` drove all three steps and reported `completed` after 8.2s. Not one stats
field moved.

```
before  starts 4 · completions 1 · step views 4/2/1 · last_played 05:34
run     browser_run_tour → {"status": "completed"}   (8.2s)
after   starts 4 · completions 1 · step views 4/2/1 · last_played 05:34
```

**Cause:** the extension's player drives the host DOM directly and never posts the
`tour.step_viewed` / `tour.completed` events the widget player emits.

**Not isolated** — see KB-3. Agent activity over MCP is systematically missing from analytics.

### KB-3 — MCP searches never reach Search analytics (Medium)

Three `search_knowledge` calls returned three hits each and left *Search analytics* reading
"No search activity yet".

```
before  queries.total 0 · top_queries 0 · ai.runs 4
3 × search_knowledge → 3 hits each
after   queries.total 0 · top_queries 0 · ai.runs 4
```

`ai.runs` *does* track, so the pipe isn't dead — the query log just isn't written on the MCP
path. The page that exists to reveal content gaps goes blind exactly as external agents start
using the knowledge base, which is the traffic most likely to expose those gaps.

### IN-1 — anonymous visitors all read "Unknown" (Medium)

Four live conversations stacked up reading *Unknown* against a *?* avatar, impossible to tell
apart. The backend already has a better answer for the same contact — the message API returns
`author_name: "Visitor"`. The list doesn't use it. The accessible name also says "unknown
contact" while the visible label says "Unknown".

### IN-2 — floating widget UI overlaps itself (Medium)

With a banner tour running, the bottom-right corner stacks chat launcher + checklist launcher +
tour pill, and the pill covers the checklist button almost entirely. Stopping the tour reveals
the *Getting started 0/3* button underneath. Same class as the toast-over-button bug already
fixed — the corner needs one stacking context that lays its occupants out.

### UI-1 — "Settings" cut mid-row (Medium)

```
nav content 596px in a 572px scroller → 24px hidden
reachable: scrolls, and is clickable once scrolled
```

24px is a spacing problem, not a layout one: tighten section gaps, or bring the user card inside
the scroll area so the cut can't land mid-row.

### KB-2 — the offline demo of the flagship feature looks broken (Medium)

Retrieval is right (asked how to install the widget, found "Getting started & installing the chat
widget"), but the answer was the generic *"a teammate or I will help you right away."* The mock
provider **can** answer extractively — `_compose_text` in `backend/app/ai/local.py` only does so
when context arrives as `role: tool` messages, and the ask path doesn't send it that way. Mock
provider only; a real model would use the context. It's the demo and seeded workspace that suffer.

## Two readings withdrawn after measuring

Recorded because both looked like serious bugs on first sight:

1. **"WebSocket reconnect storm"** — 42 failures and 21 distinct tokens in 40s turned out to be
   stale console-buffer history from 18 rapid navigations. Filtered by timestamp, a settled page
   shows **zero** WS errors.
2. **"New conversations never arrive"** — they arrive as `status=pending`, which the UI labels
   **AI**, not **Open** (the default tab). Re-tested on the right tab: live in under 3s.
